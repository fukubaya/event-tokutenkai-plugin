# Event & Tokutenkai Information Flyer Design Rules

アイドル・アーティストのリリースイベント（リリイベ）、ライブ、特典会（撮影会・お話し会・お渡し会）等の告知フライヤー・案内資料など、「印刷（A4ベクターPDF）またはWEB画像（高解像度PNG）出力」を前提とした情報デザインタスクにおける行動原則です。

## 1. 原則: 画像生成AIでの文字・表の一発出し禁止
- 画像生成AI（Diffusionモデル等）を使って、文字や数字、表を含む1枚画像を生成して完結させてはならない。文字の崩れや誤字、罫線の歪み、編集不能のリスクを回避するため。
- キービジュアル（背景やイラスト素材）のみを画像生成AI（またはSVG）で用意し、**文字・フォント・表・レイアウトはコード（HTML/CSS）として記述・分離**すること。

## 2. デザイン・レイアウトの分離とトークン管理
- **デザイントークン（カラーセット、フォント、余白）の分離**:
  - `theme.css` 等で `:root` に CSS変数（カスタムプロパティ）を定義し、カラーパレットや余白（`--page-margin`, `--color-primary` など）を一括変更可能にすること。
- **印刷サイズと裁ち落としの明示**:
  - 必ず `@page` で物理サイズ（A4, B5, mm単位）と余白を明示すること。
  - 商業印刷向けの場合は裁ち落とし（bleed: 3mm）やトンボ（crop marks）を意識した設定を設けること。

## 3. 編集性とベクター品質の担保
- **テキストと表**:
  - ラスタ画像化せず、常にテキスト要素（HTMLタグ `<p>`, `<h1>`, `<table>` 等）として保持すること。
- **イラスト・図版**:
  - 可能な限りSVGなどのベクター形式を使用し、拡大・印刷に耐えうる解像度非依存の形式にすること。

## 4. 告知ポスター・フライヤー向けデザイン指針
- **主客の明確化（来場者の最大関心事を中心としたレイアウト）**:
  - イベント告知における来場者の主たる関心事（フリーライブや特典会の内容・くじ賞品・チーム分けなど）を紙面の**主役**として扱い、最も広い面積と強い視覚的アクセントを割り当てること。
  - 準備・事務的な情報（物販ルール、入場方法、アクセス、注意事項等）は脇役としてコンパクトに整理・グループ化し、主役の視認性を邪魔しないように配置すること。
- **用紙端まで行き渡る全面背景（フチなし印刷対応）**:
  - 背景画像を使用する場合、`@page { margin: 0; }` を指定し、`body` やルートコンテナに `background-size: cover;` を適用した上で、内側のコンテンツラッパーにパディングを設定すること。中途半端な「周囲の白フチ」が発生しないように設計すること。
- **大胆なジャンプ率（文字のメリハリ）**:
  - すべての文字を均一なサイズにせず、タイトル・見出し（20〜26pt）、特典会やライブの目玉情報（11〜15pt）、本文・説明（8〜9pt）、注意事項・注釈（6.5〜7pt）と、重要度に応じた明確な階層化（ジャンプ率）をつけること。
- **重要情報（表組み等）のスペース確保**:
  - 表組み（特典会のくじ一覧、料金表等）の横に装飾画像を並べて幅を圧迫してはならない。表組みは横幅いっぱいに確保し、装飾画像は見出し横やチーム紹介エリアなどの自然なスペースにスタンプ・バッジとして配置すること。
- **時間経過（時系列順）の厳格な維持と視覚的差別化**:
  - タイムラインは来場者の当日の行動導線に合わせ、**必ず時間経過の順（例: 10:30物販 ➔ 12:25入場 ➔ 13:00ライブ ➔ 13:45特典会）で上から下へ配置し、順序を絶対に前後させないこと**。
  - 主客のメリハリは順序ではなく、「色（鮮やかなイエローやレッド）」や「カードの高さ・パディング・フォントサイズなどの占有スペースの大きさ」によって明確に目立たせること。
- **詳細情報ブロック（特典会等）の余白最適化（デッドスペースの排除）**:
  - 特典会などの大区画カード内で無駄な縦横の余白（隙間）が生じないよう、メニュー、チーム分け、案内マスコットなどを均等グリッド（3カラム等）で整然と並べ、下部に横幅100%のワイドテーブルを隙間なく配置してスペースを余すことなく有効活用すること。
- **特典会イラスト入りデフォルト作成原則（初期配置とオーバーフロー時の除外判定）**:
  - 特典会セクションなどの大区画カードは、**「原則としてイラスト入り（`skills/event-tokutenkai/assets/illustrations/` のおはなし会、2shot、グループshot等）で初期構築する」** こと。テキストのみで先行構築すると、紙面に広大なデッドスペースが生じる原因となる。
  - 最初からイラストを配置してビジュアルリッチに設計し、情報量が過密でどうしてもA4 1ページに収まらない場合に限り、イラストの縮小または除外を行う「引き算の設計」を徹底すること。
- **注意事項・お問い合わせの2カラム水平圧縮原則（縦スペース創出）**:
  - 紙面下部の注意事項リスト（箇条書き）やお問い合わせ先は、1列で縦長に並べず、**2カラム（左列・右列のフレックス配置）で水平方向に圧縮してレイアウトすること**。
  - これにより下部ブロックの縦方向占有高さを約半分（10〜15mm程度）に圧縮でき、紙面の主役である特典会テーブルや各部ビジュアルカードに十分な縦スペースを配分できる。
- **イラストのアスペクト比保護と上下トリミング防止原則（`object-fit: contain` + 白背景）**:
  - 特典会サマリーカード等でイラスト素材（正方形 1:1、1024×1024px）を配置する際、横長枠に対して `object-fit: cover` を指定すると、人物の頭部や足元、手荷物カゴ等の重要な説明描写が上下で切り取られてしまう。
  - イラストコンテナには十分な高さ（`24mm` 前後）を確保し、**`object-fit: contain;` および `background: #ffffff;`（イラストの白背景と同化）を指定して、イラスト全景（頭〜足元、小道具・案内ピクト）が絶対にトリミングされず完全に見えるようにすること**。
- **バッジ・ラベルの視認性とコントラスト比確保原則（同色化バグ防止・濃色背景×白文字の徹底）**:
  - CSSクラスで定義された文字色と、HTMLインラインの `style` 属性が干渉し、テキストと背景が同色化して文字が読めなくなる不可視化バグ（例: `.sales-priority-badge` の文字色が青系のときにインラインで青背景を指定するなど）を厳格に防止すること。
  - 濃紺（`#1e3a8a`）、赤（`#dc2626`）、橙（`#ea580c`）、紫（`#7e22ce`）などの濃色背景を持つバッジやタグには、必ず明示的に文字色を白（`color: #ffffff;`）に指定し、印刷物や画面表示において十分なコントラスト比を確保して可読性を担保すること。
- **特典会内部・タイムテーブル内のメンバー名イメージカラー（カラーチップ）表示原則**:
  - ヘッダーの出演者一覧だけでなく、**特典会テーブル内やタイムライン各項目に登場するメンバー名も、公式イメージカラーのチップ・バッジ（`.member-chip.chip-sm`）で表示すること**。
  - 「ひかる(白)・結菜(青)」のような文字での色説明は行わず、直感的なカラーチップとして彩色・グループ化することで、ファンの視線誘導と判読スピードを劇的に高める。
  - チップ内テキストには `white-space: nowrap;` を指定し、姓名間の不要な改行崩れ（「橘<br>花怜」等）を防止すること。またテーブル列幅（「実施時間＆対象メンバー」等）はカラーチップが1行に収まる十分な幅（25〜28%程度）を確保すること。
- **タイムテーブルの時刻表示（ピルバッジ）のサイズ・フォント統一と大型化（複数時刻表示対応）**:
  - 時刻は来場者の行動導線において最重要情報であるため、フォントサイズは小さく縮小させず**大きめの太字（単一時刻は11.5〜12pt、複数時刻でも10.5pt以上）**で統一すること。
- **フロアマップ（D2図）の公式発表有無による作成判定原則（推測による架空マップ作成の絶対禁止）**:
  - 会場フロア図（D2スクリプト/SVG）は、**公式告知ページにエリア分け図面や配置図が明確に掲載・発表されている場合のみ作成すること**。
  - 公式に明確なマップが存在しない、またはレイアウトが不明な場合、**推測で架空のフロアマップを作成してはならない**。特に、時間が異なるだけで同一の部屋・場所で行われる複数の部（例: 1・2部と3部）を、あたかも別のエリアや別室であるかのように図解すると、来場者に重大な誤認を与える。
  - 公式図面がない場合はマップ枠を設けず、「当日の参加フロー（1受付 ➔ 2整列 ➔ 3荷物預け ➔ 4入場）」と「共通ルール・ピクトグラム（スマホ限定、手ぶら、LivePhoto禁止等）」の左右構成やテキストによる整理を行い、その分特典会テーブルやスケジュールのスペースを最大化すること。
- **フロアマップ（D2図）と入場案内ステップバッジ・テキストの配色完全同期原則**:
  - 会場フロア図（D2スクリプト/SVG）で定義した各エリアのカラーパレット（例: お子様エリア=薄オレンジ `#ffedd5`、新規エリア=薄黄緑 `#bbf7d0`、優先エリア=薄イエロー `#fef9c3`、フリーエリア=薄グレー `#f8fafc`、カメラエリア=スレート `#cbd5e1`、グルショ前方=オレンジ `#fdba74` 等）と、入場案内リストのステップ番号バッジ（1, 2, 3, 4等）および注記テキストの背景色・ボーダー・文字色を**1対1で完全に同期**させること。
  - 図とテキストで色が異なると、照合時に認知負荷や誤解が生じるため、図の配色を唯一の基準として説明側のバッジ色を厳格に揃えること。
- **新規・カムバック・先行特典（券不要枠）の特典会テーブルへの正式統合原則**:
  - 「新規・カムバック＋紹介者向けフリーお手振り会」などの無償・条件付き先行特典会は、テーブル外の別枠テキストとして追記してはならない。必ず**特典会テーブルの最上行（先行枠／`#` は「先行」バッジ）として正式に組み込む**こと。
  - 必要参加券カラムには **「券不要」** と明記し、条件欄に「（新規/復帰＋紹介者）」等を記載することで、メニュー全体の時系列とレギュレーションが1つの表に集約され、重複や見落としを防ぐ。
  - 進行フローバー（`先行 フリーお手振り ➔ ① ➔ ② ➔ ③ ➔ ④`）にも時系列通りに反映すること。
- **タイムテーブル項目の事実純化と装飾的惹句・ポエムの完全排除原則**:
  - タイムライン各枠に、「〇〇屋上特設ステージでの全開パフォーマンス！」「最高の熱気をお届け！」などの**装飾的なキャッチコピーやポエム文を記述してはならない**。
  - 来場者の目的は当日の行動導線とスケジュールの事実把握であるため、「ミニライブ（約45分）」「観覧無料」といった客観的事実のみを端潔に記載し、無駄な文字で紙面を圧迫させないこと。
- **自明な事務的定型文（「なくなり次第終了」等）の排除原則**:
  - 特典券や優先入場券について、「定員に達し次第終了」「なくなり次第終了」「配布終了」といった**参加者にとって当たり前の自明な定型文は一切記載しないこと**。
  - スペースは極めて限られており、当たり前の定型文で文字数を増やして視認性を落とすことを厳禁とする。
- **特典会テーブルの進行順カラムの極小化（数字のみ）または省略原則**:
  - 特典会テーブルの「進行順」カラムは、ヘッダーを「#」または「順」とし、セル値は「1」「2」といった**数字のみを中央配置**すること（「①最初」「第1部」等の余分な文字は不要。先行枠は「先行」バッジ）。
  - 進行順が公式に発表されていない、または不明なイベントの場合は、**「進行順」カラム自体を完全に削除**し、その分内容・レギュレーション欄の横幅を最大化すること。
- **ピクトグラム・アイコン・絵文字による文字削減原則**:
  - 文字を長々と読ませず、直感的に0.1秒でルールが伝わるよう、Skiaクラッシュを防止するベクターSVGピクトグラム（`skills/event-tokutenkai/assets/icons/`）を活用して文字を置き換えること:
    - **ライブ・ステージ**: `mic.svg`（ライブ・MC）、`camera.svg`（撮可TIME）、`video.svg`（動画可）、`cheering.svg`（声出しOK）、`no-camera.svg`（撮影禁止）、`no-video.svg`（録画禁止）、`no-jump.svg`（ジャンプ・リフト禁止）、`no-stepladder.svg`（脚立・踏み台禁止）、`no-umbrella.svg`（傘・日傘禁止）
    - **特典会・撮影会**: `talk.svg`（個別お話し会）、`two-shot.svg`（2shot撮影）、`group-shot.svg`（グループshot）、`hand-wave.svg`（お手振り会）、`smartphone-only.svg`（スマホ限定）、`no-touch.svg`（接触禁止）、`no-prop.svg`（小道具持たせ禁止）、`no-sit.svg`（着席強要・しゃがみ禁止）、`no-screen-record.svg`（画面録画・LivePhoto禁止）、`bag-basket.svg`（手ぶら整列・荷物カゴ）
    - **物販・決済・入場**: `ticket.svg`（特典券・参加券）、`cash.svg`（現金）、`credit-card.svg`（クレジットカード）、`qr-pay.svg`（QR・電子マネー）、`clock.svg`（時計・時刻）
    - **安全・施設・汎用**: `location.svg`（会場ピン）、`warning.svg`（注意・警告）、`check-ok.svg`（OK・許可）、`prohibit.svg`（NG・禁止）、`sun.svg`（熱中症対策・屋外案内）
  - これらにより、冗長な説明文を大幅に削ぎ落とし、すっきりとした余白と高い視認性を実現すること。
- **参照元URLと印刷用ベクターQRコードの配置原則**:
  - Webの一次情報や最新スケジュールへのアクセスを担保するため、紙面下部等に参照元URLとQRコードを配置すること。
  - 印刷物での読み取り精度を担保するため、QRコードはラスタ画像（PNG等）ではなく**ベクター形式（SVG）**で生成し（例: `npx qrcode "<URL>" -t svg -o qr.svg`）、拡大縮小でも劣化しないようにすること。
  - カメラ読み取りの信頼性のため、物理サイズは最小でも `15mm × 15mm`（推奨 `16〜20mm`）を確保し、十分なクワイエットゾーン（白余白）を設けること。また、カメラが使えない環境やURL直接確認に備えてURLテキストも必ず併記すること。
  - **【極めて重要・絶対禁止】SVG QRコードの `<img>` 要素への直接 `padding` / `border` / `border-radius` 指定の禁止（Chromium / Skia PDF レンダラーの縦ストローク縮退・スダレ線化バグ防止）**:
    - Chromium / Puppeteer（Skia PDF）において、SVG形式のQRコードを表示する `<img>` タグ自体に CSS で `padding`、`border`、`border-radius`（さらに `box-sizing: border-box`）を直接適用すると、サブピクセル計算の丸め誤差によって縦ストローク（垂直パス）が縮退・クリップされ、QRコードが横縞の「スダレ線」になってカメラ読み取りが完全に不可能になる現象が発生する。
    - **正しい実装**:
      - `<img>` タグ自体には `width: 15.5mm; height: 15.5mm; display: block;` のみを適用し、`padding: 0; border: none;` とする。
      - 白座布団（背景色）や枠線、パディングを設けたい場合は、必ず親のラッパー要素（例: `<div class="qr-container">` や `<div class="qr-box">`）側にスタイルを付与すること。
- **印刷用CSSにおける `box-shadow` / `drop-shadow` / `mix-blend-mode` の禁止（アーティファクト・背景透過漏れ防止）**:
  - Chromium/Puppeteer等のPDFレンダラー（Skia）において、CSSの `box-shadow`、`filter: drop-shadow`、`mix-blend-mode`（例: multiply）は、PDF出力時に半透明な四角いバウンディングボックスや、レイヤー分離・タイリング境界における細長い背景画像の透過漏れ（スリット状のシーム）を引き起こす。
  - 印刷用PDFではこれらを完全排除し、カード背景にはプレーンなソリッドカラー（白 `#ffffff` 等）を使用し、クッキリとした `border`（境界線）やコントラストによって立体感と視認性を担保すること。
  - 白背景のイラスト画像（ステッカー等）は、ブレンドモードに頼らず白背景のカード上に直接配置することで、エッジを美しく同化させつつ透過バグを完全に防止できる。

- **開催場所・会場情報の配置原則（ヘッダー統合と独立カード廃止）**:
  - イベント告知において最重要情報の一つである「会場・開催場所」は、タイムテーブルの時刻列と混同しないよう、**必ずヘッダーカード内に統合（`.header-loc-row`）して配置**すること。
  - タイムライン先頭に「10:00〜 会場情報」などの独立カードを置くことは、貴重な縦スペース（約15mm）を圧迫し全体の窮屈さを招くため禁止する。
  - 施設名、フロア名、注意書き（待機不可・時間厳守）をヘッダー内にコンパクトに整理して配置し、時系列タイムライン（物販・入場・ライブ・特典会）との主従関係を明確にすること。

- **ヘッダー内Flexレイアウトのオーバーフロー防止原則**:
  - ヘッダー等で左右分割フレックス配置（タイトル・会場情報 vs 日付・開始時刻バッジ）を行う際、テキスト要素（会場名、住所、注意事項等）に `white-space: nowrap` を多用すると内在幅が紙幅を超え、右側の要素（日付バッジ等）を用紙外へ押し出す原因となる。
  - 左側コンテナには `flex: 1 1 auto; min-width: 0;` を指定し、住所などの冗長な表記を簡潔化（例: 施設名＋フロアのみ）してフォントサイズを最適化し、紙面幅内に確実に収めること。

- **初回作成時における複数イメージ／配色のパターン提示**:
  - クライアントやユーザーへの初回提案時は、単一のデザインに絞らず、世界観や受ける印象が異なる「複数パターン（3パターン程度）」を同時に設計・提示すること。
  - トークン分離アーキテクチャ（HTML構造と `theme-*.css` の分離）を徹底することで、共通のセマンティックHTMLを活かしたまま、低コストで配色・タイポグラフィ・演出を切り替えたバリエーションを提供できる。

- **フォントの脱・画一化と世界観に応じたタイポグラフィ選定**:
  - 「ポップだから丸ゴシック」と画一的に決めつけず、対象グループや作品・イベントのコンセプトやトーン＆マナーに最も合致するフォントスタックを選定すること。
  - **公式リサーチの徹底**: 公式サイトのInspectや楽曲・ビジュアル資料を調査し、公式が採用しているWebフォント（例: `Shippori Mincho`, `Jost`, `Cormorant Garamond` 等）やグループコンセプト（例: ロック、天使、ストリート等）を積極的に取り入れること。
  - **タイポグラフィのバリエーション例**:
    - **エッジの効いたモダン角ゴシック + ジオメトリック欧文**（例: `Noto Sans JP` / `M PLUS 1p` + `Jost`）: ポップ＆ロック、洗練されたモダンカルチャー、スクール感
    - **優美なしっぽり明朝 + クラシカルセリフ欧文**（例: `Shippori Mincho` + `Cormorant Garamond`）: 天使・透明感・愛・気品・幻想的な世界観
    - **極太角ゴシック + コンデンスド欧文**（例: `Noto Sans JP 900` + `Oswald`）: ライブハウス、フェス、タワーレコード風の熱気とインパクト
  - **Mac / Windows のOS標準インストールフォント活用原則**:
    - 外部Webフォント（Google Fonts等）だけに過度に依存せず、実行環境（macOS / Windows）にインストールされていることが前提とできる高品質なシステム標準フォントをスタック上位に指定すること。
    - **macOS 標準**: `"Hiragino Sans"`, `"Hiragino Kaku Gothic ProN"`（角ゴシック）、`"Hiragino Mincho ProN"`（明朝）、`"Hiragino Maru Gothic ProN"`（丸ゴシック）、`"Helvetica Neue"`, `"Arial"`, `"Impact"` 等
    - **Windows 標準**: `"Yu Gothic"`, `"Meiryo"`, `"Segoe UI"`（角ゴシック）、`"Yu Mincho"`, `"MS Mincho"`（明朝）、`"BIZ UDPGothic"`（丸ゴシック）、`"Arial"`, `"Impact"` 等
    - **フォントスタックの優先順位構成**:
      1. 目的に応じた欧文・数字フォント（例: `"Jost"`, `"Impact"`, `"Cormorant Garamond"`, `"Quicksand"`）
      2. macOS高品質システムフォント（`"Hiragino Sans"`, `"Hiragino Mincho ProN"` 等）
      3. Windows高品質システムフォント（`"Yu Gothic"`, `"Yu Mincho"`, `"Segoe UI"` 等）
      4. 汎用Webフォントおよびフォールバック（`"Noto Sans JP"`, `"Noto Serif JP"`, sans-serif / serif）
    - これにより、外部ネットワークへの過剰な依存やフォント取得遅延・タイムアウトを根本的に防ぎ、ローカル環境でミリ秒単位の超高速レンダリングと極めてシャープな印刷品位を両立する。
  - **Google Fonts のウェイト最小化原則（Vivliostyle CLIクラッシュ防止）**:
    - 日本語Webフォント（特に `Shippori Mincho` など）を Vivliostyle 等のヘッドレスChromiumベースのレンダラーで読み込む際、ウェイトを多数（500, 700, 800等）指定すると分割.woff2ファイルの過剰フェッチにより内部タイムアウト（`Page.printToPDF: Printing failed`）が発生する。印刷用HTMLでは、必要なウェイトを最小限（例: `wght@700` のみ）に絞ること。

## 5. AI生成画像の安全かつ効果的な部分利用

- 人物や文字をAIに描かせると不自然さや文字崩れが発生するため、AI画像生成は以下の用途に限定して活用すること:
  - **背景テクスチャ・風景**（例: 季節を感じる水彩画風の空や装飾フレーム、文字を邪魔しない明るい背景）
  - **ワンポイントのマスコット・アイコン**（例: ステッカー風のキャラクターやオブジェクト）
- 生成した画像はベクターのHTML/CSSレイアウトの「背景」や「挿絵」として重ね合わせることで、破綻のない高品質なデザインを実現する。

## 7. イベント現場即応のための情報構造化原則

- **一次情報の構造化抽出ツール先行実行原則（AI独自判断による拾い漏れ・解釈揺れの防止）**:
  - イベント告知URLや案内テキストを受け取った際、**AIが自身の場当たり的な判断で情報を拾い集めてはならない**。担当エージェントごとに着眼点やフォーマットがブレて、重要なレギュレーション（購入上限、ループ可否、優先観覧集合時間、撮可制限、注意事項等）の脱落や重複が発生するためである。
  - 必ず最初に `flyer.py extract <URL> -o event_summary.md --json event_data.json` を実行し、決定論的に整理されたスキーマ（Markdown / JSON）を出力・確認した上で、その構造化データを単一の情報源（Single Source of Truth）としてフライヤーHTMLのコーディングに着手すること。
  - 添付画像（タイムテーブル表、フロアマップ等）が告知に含まれる場合は、必ず画像も確認してテキストにない特記事項（撮可条件、入場順、ブロック制、レーン交代順等）を100%拾い上げること。
- **観覧エリア図（フロアマップ）のD2記述・ベクターSVG原則（HTML div構築の絶対禁止 ＆ グリッド箱区切り設計）**:
  - 会場フロア図（ステージ、優先観覧エリア、女性専用エリア、カメラエリア、新規エリア、フリーエリア等）を **HTML/CSS（`div`タグの入れ子）で無理やり組むことを禁止する**。包含関係（優先エリア内の新規・カメラ・女性エリアや、優先エリア前方のグルショ参加者枠など）が歪み、誤った配置図となるためである。
  - **D2 グリッド箱区切り設計原則（`templates/d2/` および過去SVG参照）**:
    - フローチャートの矢印（`->`）ではなく、**「箱（グリッド）」で領域を整然と区切るレイアウト**として記述すること。
    - **会場構成に応じた2大配置パターン**:
      1. **横長配置パターン（`direction: right`）**: ステージが左、フリーエリアが右（アリオ橋本、HMV等）
         - 最外層コンテナ（`wrapper`）に `direction: right`、`grid-columns: 3〜4`、`grid-rows: 1` を指定し、左から右へ「Stage ➔ （お子様エリア） ➔ 優先エリア ➔ フリーエリア」を並べる。
         - 優先エリア内部も `grid-columns: 3`、`grid-rows: 2〜3` のグリッドとし、前方・後方のサブエリア（新規、女性、カメラ、グルショ等）を配置し、空きマスは透明なダミー要素（`style.fill: transparent; style.stroke: transparent`）で埋める。
         - **【D2のグリッド配置順の注意点】**: `direction: right` のコンテナ内では、要素は「行ごと」ではなく**「列優先（列1上➔中➔下 ➔ 列2上➔中➔下 ➔ 列3...）」で埋められる**。そのため、3x3グリッドで「左上が新規、左下が女性、中下がカメラ」とする場合は、列1（新規・空・女性）、列2（空・空・カメラ）、列3（空・空・空）の順序で記述すること。
         - テンプレート: `floormap_grid_nested.d2`, `floormap_grid_front.d2`
      2. **縦長配置パターン（`direction: down`）**: ステージが上、フリーエリアが下（ステラタウン大宮、吉祥寺パルコ、タワーレコード渋谷等）
         - 最外層コンテナ（`wrapper`）に `direction: down`、`grid-columns: 1`、`grid-rows: 3〜4` を指定し、上から下へ「Stage ➔ 優先観覧エリア ➔ 一般フリー観覧エリア」を並べる。
         - 優先エリア内が複数枠（女性限定、新規、ファミリー等）に分かれる場合は、行コンテナ（`priority_row`, `sub_row`）に `grid-columns: 2` などを指定して左右並列で配置する。
         - テンプレート:
           - `floormap_v_simple.d2`: シンプル3段（上: Stage ➔ 中: 優先 ➔ 下: フリー）
           - `floormap_v_nested.d2`: 優先エリア内左右分割・多層（上: Stage ➔ 優先(女性限定等) ➔ ファミリー等 ➔ 下: フリー）
           - `floormap_v_tiered.d2`: 前方段状（上: Stage ➔ 前方特設(女性・子ども等) ➔ 優先 ➔ 下: フリー）
    - **外枠余白の排除（`--pad 0` 原則）**:
      - D2 デフォルトのパディング（100px）はフライヤー内のフロアマップを縮小させ文字を小さくしてしまうため、コンパイル時は必ず `--pad 0`（外枠余白ゼロ）を指定して文字サイズと視認性を最大化すること。
  - 必ず D2言語スクリプト（`floormap1.d2`, `floormap2.d2` 等）として記述し、`flyer.py d2` または `flyer.py all` の自動コンパイル機能を用いて高精度・クリーンなベクターSVG（ライトテーマ `--theme 0 --pad 0`）を生成・配置すること。
  - フロアマップは開催場所ではなく、必ず **【観覧エリア入場案内枠】（`.card-step-entry` の右側 `.entry-map-col`）に配置** すること。入場集合・呼び出し順の文脈と一体化して初めて現場で機能する。
- **入場案内枠への情報集約原則（カメラエリア規定・整理番号呼び出しブロック）**:
  - 会場への入場に関わる規定（カメラエリアの機材制限・注意事項、整理番号の呼び出し順・ブロック巡回ルール）は、ミニライブ枠ではなく **必ず【入場案内枠】（`.card-step-entry`）に集約配置** すること。
  - ミニライブ枠（`.card-step-live`）は「開演時刻・撮可曲・じゃんけん大会・コール＆レスポンス等のマナー」といったステージ本編の進行事実に純化し、情報が分散して来場者が迷うのを防ぐこと。
- **特典券システムの2大分類（共通券消費型 vs メニュー別専用券型）の峻別原則**:
  - アイドル・アーティストの特典会には、以下の2つの全く異なる特典券システムが存在する。これを混同し、**「商品購入枚数（N点購入）」を「必要な特典券の枚数（N枚消費）」と混同して記載することは重大な現場トラブルを招くため厳禁**とする。
  1. **【共通券消費型（単一特典券プール型）】**:
     - **代表例**: Straight Angeli、RE-GE、スタープラネットアイドルアカデミーなど
     - **仕組み**: 対象商品1点購入（または〇〇円購入）ごとに共通の「特典券」が1枚（または購入点数分）渡され、メニューごとに必要な枚数（例: 1枚でお見送り、2枚で個別サイン、3枚で2shot）を消費して参加する。
     - **フライヤー表現**:
       - 物販付与列: 「特典券 1枚」「特典券 2枚」
       - イラストバッジ: `[特典券 1枚]`, `[特典券 2枚]`, `[特典券 3枚]`
       - 特典会テーブル列見出し: `必要特典券`（または `必要枚数`）: `1枚`, `2枚`, `3枚`
  2. **【メニュー別専用券型（商品引換・専用券1枚型）】**:
     - **代表例**: ばってん少女隊（ちゅぴ リリイベ等）
     - **仕組み**: 特典券自体がメニューごとに別々の券種（「①動画お手振り券」「②お話し/10秒動画券」「③2shot券」「④グルショ券」等）として分かれており、**どの特典会メニューも参加時に提出する特典券は「各専用券 1枚」**である。メニューごとの違いは、物販レジでその専用券をもらうために必要な**対象商品の購入点数（例: 1枚購入で①〜③から1枚選択、2枚購入で④グルショ券1枚）**である。
     - **フライヤー表現**:
       - 特典会テーブルの列見出しを「枚数: 2枚」などと書くことは厳禁（共通券を2枚集めて出すと誤解される）。
       - 物販付与列: `1枚購入 ➔ ①〜③より希望の専用券1枚選択` ／ `2枚購入 ➔ ④グルショ専用券 1枚`
       - イラストバッジ: `[専用券 1枚 (商品1枚)]`, `[専用券 1枚 (商品2枚)]`
       - 特典会テーブル列見出し: `必要参加券 (商品購入条件)`
       - 特典会テーブルセル: `専用券 1枚 (対象商品1枚)`, `専用券 1枚 (対象商品2枚)`
  - 「1会計につき優先券1枚（ランダム番号）」「購入上限数（当日アナウンス等）」「ループ可否」も物販セクションの見出し直下にバッジとして目立つように配置すること。
- **公式風イラスト素材の体系的活用原則（デッドスペース解消と視覚的直感性の両立）**:
  - 特典会は来場者の最大関心事であり紙面の主役である。大区画カード内で余白（スカスカ）を残してはならない。
  - `skills/event-tokutenkai/assets/illustrations/` に同梱されている公式風イラスト素材（`tokuten-video-sendoff.jpg`, `tokuten-talk.jpg`, `tokuten-2shot.jpg`, `tokuten-group-shot.jpg` 等）を特典会ビジュアルストリップ（`.tokuten-visual-item` > `.tokuten-illust`）に配置すること。0.1秒でイベント内容が直感的に伝わり、紙面全体のプロフェッショナルな情報密度を飛躍的に向上させることができる。
  - イラスト配置に加えて、手荷物案内・熱中症対策・公式X進行状況確認などの「現場情報ストリップ（`.tokuten-info-strip`）」を配し、紙面下部のデッドスペースを余すことなく有効活用すること。
- **「撮可（撮影可能）TIME」と「特典会（撮影会）」の厳格な峻別**:
  - **撮可TIME（ライブ・イベント中）**:
    - ライブ・イベント本編中は**「原則として撮影禁止」**であるため、その中で特別に設けられる「撮影可能な指定時間帯」を指す。
    - 撮可TIMEであっても、**静止画のみ / 動画OKの制限**や、**機材の制限（スマホ限定、コンデジ可、一眼レフ可、一脚・三脚・フラッシュ禁止等）**がイベントごとに厳密に指定される場合がある。公式に指定された条件をそのまま記載すること。
    - **「指示がない場合での撮影禁止」の勝手な全面禁止断定の禁止**: 「メンバー・スタッフからの指示がない場合での写真撮影、動画撮影、録音行為は固く禁止します」という公式告知は、**指示があればOK（＝撮影可能TIME）**を意味する。短く表現したいからといって「撮可TIMEの実施はありません」「撮影・録音 全面禁止」と勝手に決めつけて要約してはならない（意味が変わる重大な誤記となる）。短縮する場合も「【撮影・録音：指示時のみ可】メンバー・スタッフの指示がある場合を除き禁止」など、条件付きであることを正確に表現すること。
  - **撮影会（特典会）**:
    - ミニライブ終了後、対象商品購入等で得た「特典券」を消費して参加する個別/グループ撮影イベントを指す（例: 2shot撮影会、動画お手振り会等）。機材は「スマホ限定（一眼・コンデジ不可）」とされることが多い。
  - これらを「写真が撮れる」という共通項だけで絶対に混同・同一視せず、別セクション・別レギュレーションとして明確に区別して表記すること。
- **物販・特典会における購入レギュレーション（点数制限・組み合わせ・ループ可否）の明示**:
  - リリースイベントや特典会には、混乱防止や公平性のため独自の購入レギュレーションが設けられることが一般的である。
    - **1度の会計での購入点数（上限数）**: 1会計につき◯点まで、または「上限数は当日発表」等の制限。
    - **商品の組み合わせ制限**: 同一品番・形態の複数購入制限や、特定盤種とのセット購入条件等。
    - **ループ（買い増しのための並び直し）の可否**: 1度会計を済ませた後に再度列の最後尾に並び直して2回目以降の購入・特典券獲得を試みる行為の可否（例: 「平日開催のためループ不可で販売開始」「状況により解除」「ループ可能」等）。
  - これらはファンの当日行動（資金計画や整列戦略）における最重要情報であるため、注意事項欄に埋もれさせず、商品販売タイムライン枠の直下に目立つアラートバッジ（赤枠・ハイライト等）として目立つように明記すること。
- **一次情報にない事実の推測禁止と、禁止事項の過不足排除（事実の厳格性原則）**:
  - **サイトに書かれていないことを勝手に推定して明示してはならない**。間違った情報を伝えることは現場の重大なトラブルにつながる。

- **Chromium / Skia PDF レンダラーの内部クラッシュ（`Protocol error (Page.printToPDF): Printing failed`）完全防止ガイドライン**:
  - **絵文字フォールバッククラッシュの防止**:
    - `⚠️`（U+26A0 + 異体字セレクタ VS16 `\ufe0f`）、`🧎`（しゃがむ人）、`🗣️`（話す人）などの特定のOpenType絵文字は Chromium のフォント解決時に Skia で内部クラッシュを引き起こすため使用禁止。
    - 警告には `⛔` やテキスト表記を用い、実績のある安全な絵文字（`📸`, `💬`, `🎒`, `📱`, `🤝`, `👋`, `👥`, `🎥`, `⭕️`, `❌` 等）のみを使用すること。
  - **サブピクセル境界線（`border: 0.3pt / 0.4pt`）の丸め誤差クラッシュ防止**:
    - ネストされたFlexbox内のインラインバッジ（`.manner-pill-*`, `.prohibit-pill`, `.faq-badge` 等）に極小サブピクセル（1px未満の `0.3pt / 0.4pt`）の border を適用すると、Skia の幾何計算が破綻してクラッシュする。
    - バッジ類には border を使わず、背景色と文字色の十分なコントラスト＋ `border-radius: 0.4mm` のプレーンバッジとすること。
  - **Flexbox内のCSS Gridネスト禁止**:
    - 印刷用Chromiumでは `display: flex` の子要素に `display: grid; grid-template-columns: ...` を指定するとレイアウト計算でクラッシュしやすいため、すべて `display: flex; gap: ...` と子要素 `flex: 1 1 0; min-width: 0;` に統一すること。
  - **物理サイズ超過による改ページ衝突クラッシュ**:
    - `@page { margin: 0; }` かつ `break-inside: avoid;` が指定されたコンテナ内で、子要素の高さの合計が 297mm をわずか数ミリでも超過すると、エンジンが改ページできずにクラッシュする。
